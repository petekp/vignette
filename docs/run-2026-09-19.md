## 1. What landed

### The annotator's frame grows in each direction on its own

`todo8/annotator`, `f4c611c`. The zoom is still one number — how far the image is magnified past
the frame it opened in — and the picture is still magnified uniformly by it, so nothing stretches.
What changed is the frame: each side is `min(fitted * level, room)` and stops at the room on its
own. `Zoom.split` now divides the level per side, so `window * camera` is the level in each
direction. A tall narrow screenshot's frame therefore widens to the whole room while the whole
width of the picture is still in view.

`Zoom.reach` and `Zoom.split` return a `CGSize`; `anchor(_:fitting:within:)` became
`anchor(fitted:within:)`, because with both sides reaching the room there is exactly one anchor per
direction and the cursor has no say in the frame's growth; `pageRatio(level:window:)` is the new
single place that says what the page is told.

Driven on the merged build, on `Screenshot tall.png` (600 x 1700 px, fitted at `[565, 98, 247,
699]`, room `[0, 38, 1377, 872]` with the recent stack open), with real Cmd+`=` presses:

## 2. Decisions made without you, and open questions

### The annotator's, carried forward

- **The frame's growth is no longer aimed at the cursor.** With both sides reaching the room there
  is one anchor per direction and no choice in it. Nothing can be cropped while the frame is
  growing, so what changes is where the picture sits on screen, not what is visible. This is a real
  behaviour change and the one thing a hand might notice.
- **No protocol bump from this branch**, because `setView`'s payload and the meaning of its `ratio`
  are unchanged. I verified the case that reasoning rests on (below).
- **A restarted web content process brings the level home first**, so the reloaded page does not
  letterbox a grown frame. Not asked for; a defect the change would otherwise introduce.

### The marks branch's, carried forward

- **0.022 of the image's width** is the pushed text's font size, one number
  (`PUSHED_TEXT_SIZE` in `web/src/config.ts`). On a 900-pixel crop the annotation comes out smaller
  than the screenshot's own UI text; on a full capture it is larger. No rule reading pixel sizes can
  match both.
- **Only text marks are pulled back inside.** A rectangle or arrow an agent places off the edge is
  still cropped.
- **An explicit `w` is used as it stands**; the 0.15 floor applies only to the default width.

### Mine, as integrator

- **The protocol bump stays at 13, once**, and both branches' payload documentation is inside it.
  `Sources/Bridge.swift` carries the annotator's rewritten `ViewRequest` comment and the marks
  branch's `Mark` note; `web/src/bridge.ts` mirrors both. Nothing else about the contract changed.
- **The annotator's "no bump" reasoning is sound, and I drove the case it rests on.** The claim is
  that `level / min(window.width, window.height)` is what `fit-max` means once the frame stops
  carrying the image's shape. On the tall fixture zoomed to level 3.0518, where the frame is
  754 x 872 against an image of 300 x 850 points, the page painted exactly what the host asked
  (`ratio=2.4463 painted=2.4463`), and `page.zoom` equalled it. Five levels, five agreements, zero
  mismatch lines.
- **I kept `safeBottom`'s reading at your own Dock and did not widen it.** At `tilesize 51`, bottom,
  no autohide, the Dock's tiles are 966 points wide and end at x ≈ 1239, while the column starts at
  x 1307. So `safeBottom` is 0 and the column runs to y 965, the screen's bottom less
  `ui.screenMargin`. That 0 is a successful reading, not a failed one: `Dock.tiles()` returning nil
  makes the caller reserve the whole edge instead. The step-around itself is therefore not
  exercised at your Dock width — it needs a wider Dock, and last night's lesson is that widening it
  is what hides a bad reading, so I left it alone.

### Open questions for you

1. **Try the zoom on the trackpad**, on a tall narrow screenshot and a wide short one. A real pinch
   and a real two-finger double tap are the one input `CGEvent` cannot post, so neither agent nor I
   have felt it. The window should widen and heighten until each side reaches the edge of the space
   it has; for a tall image the whole width should stay in view the whole time it is widening;
   Cmd+0 should come home to exactly the frame it opened in; nothing should stretch.
2. **Is 0.022 the right size for a pushed text?** One number in `web/src/config.ts`. It is a taste
   call about where between "smaller than the screenshot's own UI text" and "a clear callout" to
   sit.
3. **Should a rectangle or an arrow be pulled inside the image too?** Today only text is.
4. **`annotator.zoom` and `annotator.canvasZoom` are pairs now.** Any script you have that reads
   them as numbers needs a change. This is the second state-report contract change in two nights.
5. **The toolbar's slide takes as long as the card's flight takes to reach the frame.** If it reads
   as lagging the image, the number is `AnnotatorToolbar.slideSeconds`.
