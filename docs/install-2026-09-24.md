# Installing and first launch, 2026-09-24

Before the first public release, I tested a download and first launch from start to finish. I used
test copies with their own bundle ids, and one was notarized so Gatekeeper treated it as a real
download. Five problems came up. Each one is fixed in the same change as this note.

## What was wrong

1. **A Desktop user's first launch hung.** `ScreenshotWatcher.init` listed the watch folder on the
   main thread. For a folder macOS protects, that read waits until the user answers macOS's
   "would like to access files in your Desktop folder" prompt. The launch sat for 4 minutes 20
   seconds with no setup window and no menu bar icon, which was as long as the prompt stayed up.
   The Desktop is where macOS saves screenshots unless you change it.
2. **Don't Allow failed silently.** The watcher logged `Operation not permitted` and nothing else
   happened. The setup window kept asking for a screenshot it could never see.
3. **Allow in System Settings raised two things at once.** It called
   `AXIsProcessTrustedWithOptions` with the prompt and opened the Accessibility pane. The pane came
   up in front, and macOS's alert waited behind it. After the switch was on and System Settings
   closed, the alert was still there asking the same question. Each further press queued another
   alert to come up after it.
4. **Launch at login was off.** The first launch turns Apple's thumbnail off. After a restart, every
   capture was silent until the user opened Vignette again.
5. **Opening the app from the disk image stranded it there.** The app ran from the read-only
   volume. A login item registered there points at a path that goes away with the image, and the
   image could not be ejected while the app ran.

## What was measured

- **Folder prompt.** With the first listing on the watcher's queue, the launch took 0.6 s
  including the 0.5 s wait, and the setup window came up under macOS's prompt. After Don't Allow and
  a later Allow, the retry picked the folder up within 2 s, with no relaunch. It logged
  `[watcher] watching … after an error`. The 5 images already on the Desktop were indexed without
  being reported as captures.
- **Accessibility alert.** macOS showed its alert within half a second of each request, including
  for an app already listed in the pane with its switch off. The app reads the alert's window owner,
  `universalAccessAuthWarn`, without Screen Recording permission. After the fix, a press brought up
  the alert alone, and its button opened the pane with the app listed.
- **Notarized disk image.** A stapled, notarized image opened from a quarantined download ran the
  app from `/Volumes/<name>`, not from an App Translocation path, so the read-only volume check is
  the one that fires. Gatekeeper asked once. The moved copy, with its quarantine flag cleared,
  opened without asking again.
- **Eject.** `NSWorkspace.unmountAndEjectDevice` unmounted the APFS image's volume and left the
  image attached. Opening the same file again then mounted nothing. `hdiutil detach <mount point>`
  detached the whole image. The moved copy detached it on its first try, 0.4 s after the move.
- **Upgrade.** With an older copy running from `/Applications`, the move put that copy in the
  Trash, and the new copy quit the old instance on launch.
- **Login item.** Closing the setup window logged `[login] registered status=enabled`. Turning the
  setting off logged `unregistered status=notRegistered`.

## Not covered

- The toggle in System Settings needs a person, so the setup window's return to the front when
  the grant lands has not been seen yet. It logs `[setup] Accessibility granted` when it happens.
- The first capture after setup was not driven. It would have put a file on the real clipboard,
  and the watcher and copy path it uses are the same as in daily use.
