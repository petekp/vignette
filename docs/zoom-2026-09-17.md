# Zooming the annotator, rebuilt from the bottom up (2026-09-17)

Pete: "zooming the annotator is still super janky. the image within the frame is often out of sync
with the frame, or does these layout jumps and skips while zooming, sometimes getting stuck at a
position or size that doesn't match the frame."

Every claim below was measured before it was designed for: a trackpad-shaped cmd+wheel stream
driven at the page, the frame's rect and the web view's transform logged on every tick, and screen
bursts read back frame by frame. The fixture was a 1042x689 point grid whose own edge is a green
ring, opened at `[235, 103, 1042, 689]` on the built-in Retina display — the frame Pete's last
state line reported, so `maxZoom` was 1.2656 as it is for him.

## What the old design could not guarantee, with the numbers

1. **A stream that mixed step sizes teleported the window: 48 points in one frame.** The host chose
   between a spring and an immediate set per message, by the size of that message's factor
   (`abs(log(factor)) >= log(1.2)`). A spring lags its target; an immediate set jumps to it. In the
   measured flick the spring was passing 1.2034 when a smaller message arrived, and the frame went
   from 950 to 998 points wide in one tick. One gesture crosses that threshold several times, in
   both directions, and the momentum tail crosses it once more on the way out.

2. **The page magnified while the frame was still growing.** The window's scale and the camera were
   separate quantities, and the split was decided against the window's *target*, not the window on
   screen. In the same flick the camera went 1.00 -> 2.67 (2.7x) while the window went 1.17 -> 1.20
   (1.03x). That is the image and the frame out of sync, by a factor of two and a half.

3. **The image did not fill the frame on any moving tick.** The web view was laid out at
   `fitted x committedScale` and scaled by `scale / committedScale`, while the frame was
   `Zoom.frame(...).integral`. Measured: 57 of 63 ticks in one stream and 81 of 87 in another had
   the image between 0.2 and 2.0 points smaller than the frame it was inside, changing every tick.

4. **Motion ran at the page's message rate, not the display's.** The immediate-set path moved the
   window when a message arrived, so the median gap between geometry changes was 17 ms — half the
   refreshes of a 120 Hz display showed no change — with single gaps up to 153 ms.

5. **The relayout at rest showed the page at the wrong size, and the cover did not stop it.** A web
   view grown before its process has painted draws its old, smaller content in the corner of the
   new size. With the page's main thread deliberately blocked for 400 ms at the relayout, a burst
   caught the image at 1036x683 points, pinned to the top-left of a 1304x862 frame. The old cover
   came down after three page frames *or* 0.3 s, whichever was first, and was torn away outright by
   the next zoom message — so it expired while the page was still catching up. That is the
   "stuck at a position or size that doesn't match the frame".

## What owns what now

**One number.** A zoom session has a single state: `zoomLevel`, how far the image is magnified past
the frame it opened in. Everything visible is a function of it.

**`Zoom.split` divides that level in one place.** The window grows until it can grow no further,
then the page's camera takes the rest:

    split(level) -> (window, camera)      window * camera == level

So the window's scale and the page's magnification are not two quantities that have to be kept in
agreement. They are two readings of one quantity. There is no boundary where ownership changes
hands, and no step where one moves and the other has not been told yet.

**`AnnotationController` owns the frame's geometry and the image's geometry on screen.** One tick
does both:

1. `Zoom.frame(fitted:scale:anchor:within:)` gives the frame's rect. `moveFrame` sets the frame
   view, the clip and the shadow's path from that one rect, and `frameOnScreen` reads it back. A
   `frameDidChange` callback was considered, to push the rect to a shadow drawn in another window
   on every tick; that design was weighed and not built (`docs/shadow-2026-09-17.md`), so there is
   no callback.
2. `fitWebView` scales the web view's layer by **the frame's own bounds over the size the page was
   laid out at**. The image's edges are therefore the frame's edges by construction: the scale is
   derived from the frame rather than computed alongside it, so no rounding, clamp or screen-edge
   nudge can put them out of step. The frame is no longer rounded to whole points either.
3. Both are set in the same run loop turn, so they reach the window server in the same Core
   Animation commit.

**The page owns only what is inside a fixed viewport**: which part of the image is visible and at
what camera zoom, once the window can grow no further. While the window is growing, the camera is
exactly 1 and the page is not called at all.

**One spring.** Every input moves `zoomTarget`; a single `Tween` spring carries `zoomLevel` to it,
ticked by the screen's display link. Nothing teleports, so a gesture, a key, a two-finger double tap
and a fit all bend into each other, and the messages' uneven arrival (they cross a process boundary,
so two can land in one refresh and none in the next) cannot reach the screen as uneven motion.

## What happens on each input

| input | target | spring |
| --- | --- | --- |
| trackpad pinch (`magnify`, with its phases) | `level * (1 + magnification)`, about the fingers | tracking (0.1 s) |
| cmd+wheel, one message per page frame | `level * factor`, about the cursor | tracking (0.1 s) |
| fingers lift (`.ended`/`.cancelled`) | 1, if the level was pulled below it | step (0.3 s) |
| cmd+plus / cmd+minus | `level * 1.25`, about the middle | step (0.3 s) |
| cmd+0 | 1, about the middle | step (0.3 s) |
| two-finger double tap | twice the fitted size about the tap, or 1 when already zoomed | step (0.3 s) |

A gesture names the point it is over, a key names none: that is what tells the two apart, and it is
already what the bridge carries, so the protocol is unchanged.

The motion scale multiplies both springs, so `ui.motion: 0` and Reduce Motion land every step at
once. Below the fitted size the level may be pulled to 0.5 and the window shows 0.3 of the pull; it
springs back when the fingers lift, or when the spring arrives with the target still below 1.

## The one thing that still crosses the process boundary

The page has to be laid out at the size it is drawn at, or it renders soft. That resize is the only
part of a zoom the host cannot finish in one commit, and measurement (point 5 above) says the gap is
real. So it happens **once, when the spring has arrived**, on the next turn of the run loop, skipped
if a new input has aimed the zoom somewhere else meanwhile — and a picture of the page covers it.

The cover is the same pixels the live web view was already showing under its transform, stretched to
the frame, and it follows the frame, so a gesture may start while it is up and the image still fills
the frame exactly. It comes down when the page answers that it has painted (two of its frames, the
second after its resize observer has refitted), not on a timer; a two-second deadline only guards
against a page that never answers. One screen-sized bitmap exists at a time, for the length of one
relayout — measured at 19 to 32 ms in normal use.

The relayout itself is a geometric no-op: the page's `fit-max` camera fits the image to its viewport,
so growing the viewport by `k` grows the camera's zoom by `k`, which is exactly the transform the
host drops in the same turn.

## What was weighed and not taken

- **Never relaying the page out** — lay the web view out once at the largest size the frame can
  reach and only ever scale it down. This removes the resize entirely and keeps the image sharp,
  but AppKit converts event locations through view frames and ignores layer transforms, so every
  pointer inside the editor would be offset by the scale (up to 138 points at the frame's edge on
  this screen). Drawing while zoomed is the point of zooming, so this was refused. Compensating by
  overriding `convert(_:from:)` on the web view would route the whole of AppKit's event and tracking
  geometry through a hook of ours.
- **Driving the page's camera every tick instead of a layer transform.** The camera is a call across
  a process boundary; it cannot land in the same Core Animation commit as the frame's rect. That is
  exactly the drift being removed.
- **Keeping the page's old content and letting the host's transform correct it until the page
  paints.** The stale content and the new content have different geometry, so one transform cannot
  be right for both; it only moves the wrong frame from before the paint to after it.

## The picture is the app's own while a zoom moves (2026-09-17, evening)

Pete, after three passes on the design above: still janky. The cause is in the design and not in
its numbers. The frame is a layer in this process; the picture was WebKit's, composited in another
process; between rest positions it was that page's layer stretched. Two drawers with no shared
frame clock cannot be perfectly aligned, and a stretched page cannot be crisp. Photos and Quick
Look scale a native image layer during the gesture and never show a web view mid-motion.

So: **a native stand-in during the gesture, the page only at rest** (`Sources/StandIn.swift`).

- The first zoom input covers the web view with two layers inside the frame: the screenshot,
  decoded through `Thumbnailer` off the main thread, and the annotations over it as a transparent
  overlay the page rendered earlier. They are in the frame's own layer tree, so a tick sets the
  frame's rect and the picture's rect in one Core Animation commit.
- `Zoom.split` still divides the level into the window's scale and the magnification, and is still
  the only place that does. `Zoom.visible` and `Zoom.picture` turn the magnification and a centre
  into the picture's rect inside the frame; `ZoomPan` holds the point under the cursor while the
  magnification changes, as `ZoomAim` does while the window grows.
- The page is not called at all while a zoom moves. At rest the web view is laid out at the frame's
  size and given the exact view — the magnification and the middle of the visible part, as
  fractions of the image — through one call, `setView`, which answers when the page has painted it.
  Then the stand-in crossfades out, and only while the zoom is still standing still: if the spring
  moved on while the answer was in the air, the page's picture is behind the frame, so the stand-in
  stays and the next rest hands over again. That check is not a detail: without it a gesture whose
  messages paused long enough for the spring to settle showed one frame at 73% brightness.
- The web view is laid out at the frame's size **rounded up to whole points**. A layout viewport is
  a whole number of CSS pixels, so a frame 1318.8 points wide left its last fifth of a point
  uncovered and the picture ended a point short of the frame — which is exactly what stepped at the
  swap. Rounded up, the page covers the frame and the container's mask clips the fraction over.

Deleted: the web view's layer transform (`fitWebView`), the relayout cover and its deadline, and
the per-tick camera call with its one-at-a-time queue. The page now hears from a zoom once.

## The room gives way when the zoom is aimed, not part way through it (2026-09-17, night)

Pete, on the merged build: "when zooming the annotator image, it seems to be doing the arc motion
near the beginning of the transition. In this specific interaction we do not want any arc."

There is no arc in the zoom's code — `FlightCurve` belongs to card flights — so the motion was
measured before anything was changed. The fixture was a 1000x700 grid with a dark line at a quarter
of its height, opened at `[263, 103, 986, 689]` on the built-in display with the stack closed, so
the room was the whole visible frame `[0, 38, 1512, 872]` and `maxZoom` 1.2656. Every tick of
`applyZoom` logged the level, the split, the anchor and the frame; the same sequences were recorded
at 60 fps across a 40x300 point strip and read back frame by frame.

### What was moving

The fitted frame is centred left to right but not top to bottom: 65 points of room above it and 118
below. A keyboard step about the middle therefore asks for more room above than there is, and
`Zoom.frame`'s clamp took it back — every tick, once the top edge reached the room.

Cmd+plus from rest, from the tick log (120 Hz, a 376 ms spring):

| | before | after |
| --- | --- | --- |
| the anchor over the step | 0.5 for 110 ms, then given away | 0.3552 throughout |
| the picture's middle: first movement | none for 110 ms (under 0.01 pt a tick) | 0.84 pt on the first tick |
| biggest movement in one refresh | 2.54 pt, out of a standstill | 1.68 pt, decaying with the spring |
| the line a quarter down the image | up 31.6 pt, then **back down** 9.7 pt | up 18.0 pt, and stops |

The 60 fps recording says the same in device pixels: before, the line rose 63 px to row 448 and
came back 20 px to 468; after, it rises 36 px to row 474 and stays. A point of the picture that
moves one way and then turns around is what reads as an arc.

A trackpad-shaped cmd+wheel stream (24 messages, `deltaY: -1`, cursor at 0.18/0.22 of the window)
was worse, because a stream re-aims every message:

| | before | after |
| --- | --- | --- |
| movement under the cursor for the first 350 ms | under 0.013 pt a tick | 0.13 to 0.97 pt a tick |
| biggest movement in one refresh | 4.88 pt, out of a standstill | 1.06 pt |
| the anchor | 0.221, then 0.292 … 0.354 over 60 ms | 0.3552 throughout |
| the cursor's x | held to 0.011 pt | held to 0.011 pt |

The two candidates the item named were checked and cleared. The anchor blend from a previous aim
contributes nothing at the start: `ax`/`ay` are constant until the clamp bites. And the stand-in's
first frame is not a step — the first moving frame of the recording moves the picture's top edge by
3 device pixels, which is what the tick log says the frame moved.

### What changed

`Zoom.anchor(_:fitting:within:)` moves the anchor as little as the room allows, once, when the aim
is taken. The anchor it returns is the one that lets the window grow all the way to the room without
the frame ever reaching the room's edge. Each edge of the frame moves one way as the window grows,
so an anchor that fits the whole growth fits every scale on the way to it, and the frame's path from
the fitted size to the room is a straight line at one set of proportions. `Zoom.reach` is how far
the window can grow, and `AnnotationController.maxZoom` is now that same function.

The room is divided at the full growth rather than at each step's target, because a stream's target
is only ever one message ahead: clamping per step left the give-way to arrive when the room ran out,
which is the jerk again, a hundred milliseconds softer. Clamped at the reach, the anchor is settled
from the first tick of a gesture and never moves during it.

In the direction the room binds there is exactly one anchor — at the reach the frame fills that
side of the room — so the cursor's point cannot be held there, and the picture pans at a steady rate
as it grows. In the other direction the room has slack and the cursor is held exactly, which is what
the wheel stream's x column shows. The total displacement is the same as before; only its shape is.

`Zoom.aim` also starts a step from `now` rather than from an anchor read at the fitted size. At
scale 1 the frame is `fitted` whatever the anchor, so there is no growth for an anchor to describe;
blending from that made-up value bows the frame's path quadratically — up to 6 points of out and
back on this fixture — which is the arc a second time, in miniature.

The clamp in `Zoom.frame` stays as the last guard. Over a 24-message stream it moves the frame by
at most 0.09 points, a sixth of a device pixel, where the blend between two aims is not quite
straight; it also still covers a frame larger than the room.

## A cursor near an edge holds that edge in view (2026-09-17, night)

Pete: "even when putting my cursor near a corner and zooming, the corner of the image I'm hovering
still gets pushed out of frame; I'd probably need my mouse to be within a few pixels of the corner
to keep the corner from getting cropped."

He is right about the few pixels, and the geometry says why. The magnification holds the image's
point under the cursor at the cursor's own fraction of the window. With the cursor at 0.95 of the
window and the whole image in view, that point is 0.95 of the image, and the visible part of the
image runs to `0.95 + 0.05 / camera` — short of the image's right edge at every magnification above
1. Only a cursor at exactly 1 keeps the edge, because only then is there nothing of the image left
to the right of the point being held. The last five per cent of the picture is not a band where the
edge survives; it is a band where the edge goes as soon as the picture magnifies at all.

The window's own growth needs none of this. Until the window can grow no further the camera is
exactly 1 and the whole image is inside the window, so nothing can be cropped before the
magnification starts. The bias is in `ZoomPan` alone, and `Zoom.split` is still the one mapping.

`Zoom.pulledToEdges` moves the cursor onto the nearest edge before `aimPan` stores it:

- `ui.zoomEdgeBand` (0.15) is how far from each edge of the picture the pull reaches, as a fraction
  of it. On a 986 point wide frame that is 148 points.
- `ui.zoomEdgePull` (0.5) is the part of that band in which the edge is taken outright. Across the
  rest the pull eases off linearly to nothing at the band's inner edge.

So with the defaults, a cursor in the outer half of the band — within 74 points of an edge — holds
that edge exactly, and between 74 and 148 points the anchor slides from the cursor's own fraction
towards the edge. Outside 148 points the cursor is its own anchor, so the middle of the picture
zooms about itself and does not feel sticky. The two knobs are separate because they answer
different questions: how near counts as near, and how sharply near becomes pinned. A single knob
would have to trade the reach of the effect against its firmness.

The curve is linear in the depth into the band rather than eased, because what the eye judges is
where the picture ends up, not the shape of the map from cursor to anchor: the anchor is chosen once
per input and the spring does the moving. A curve that approached the edge asymptotically would
never actually pin it, which is the behaviour being replaced.

What this costs: inside the band the zoom no longer holds the point under the cursor. It holds the
edge instead, which is what was asked for — a corner beside the cursor is worth more than the exact
pixel under it.

## The edge band is a number of points, so it reaches as far from every edge (2026-09-18)

Pete: "the zoom anchoring — where we have the image stick to one side of the frame while zooming —
is great but only seems to be working on the left and right edges. we want it on the top and bottom
too."

The pull is the same code in x and y. What differed is the band it reads: `ui.zoomEdgeBand` was a
fraction of each side of the picture, and a screenshot is wider than it is tall, so a fraction of
the short side is a short band. On the fixture below — 1500 x 500 points, opened at
`[60, 215, 1392, 465]` — 0.15 reached 208.8 points in from the left and right edges and 69.8 points
in from the top and bottom. A cursor 50 points from the left edge was deep inside the half of that
band which pins; 50 points from the top edge was most of the way through a band a third as deep, so
the top edge slid out of view as soon as the picture magnified.

`ui.zoomEdgeBandPoints` (120, bounds 0…400) replaces it: how far from each edge the pull reaches,
in points of the frame the cursor is over. The same distance on every edge of the same frame,
whatever the screenshot's shape. `ui.zoomEdgePull` (0.5) is unchanged — the part of that band in
which the edge is taken outright.

Points rather than a fraction of the shorter side, which was the other candidate. A fraction of the
shorter side also makes the four edges agree, but what it means in points then depends on the
picture: the same setting reaches a different distance on a 3:1 screenshot and a 4:3 one. A
distance from an edge is what the hand is doing, and it is a unit the slider can show.

The band is measured against the frame the cursor is over, not the image and not the fitted frame,
and it reaches at most half of a side, so the middle of the picture is its own anchor whatever the
band is set to. While the window is still growing nothing can be cropped — the camera is exactly 1
until the window can grow no further — so the only frame the band has to be right for is the one
the window stops at.

A key that changed its unit is a new key: the old `zoomEdgeBand` line in a settings file is ignored
and `zoomEdgeBandPoints` starts at its default, so a tuned value does not survive the rename.

## A double-click with the select tool zooms, the way the trackpad's double tap does (2026-09-18)

Pete: "enable double tapping with the selection arrow tool in the annotator to zoom into that part
of the image."

A two-finger double tap already zooms twofold at the tap and comes home to the fitted size from
anywhere above it (`smartMagnify`, straight from AppKit). A mouse double-click reached tldraw
instead, which on the canvas created a text shape.

Who decides is split the way the rest of the zoom is. The page knows the tool and what is under the
pointer; the host knows the zoom. So the page sends one message, `smartZoom`, with the cursor as a
fraction of the window, exactly as a `zoom` message carries `at`, and the host runs the same step
the trackpad's tap runs. The protocol goes to 10.

What the page refuses to send:

- Any tool but select. The other tools draw, and a double-click while drawing belongs to them.
- A double-click while a mark's text is being edited.
- A double-click on a mark. The test is tldraw's own: the same hit-test margin, and a hollow shape
  is not hit inside, so a double-click inside an empty rectangle zooms (tldraw does nothing there)
  and one on its outline edits its label (tldraw's meaning, untouched).

`createTextOnCanvasDoubleClick` is off in the editor's options, so tldraw no longer creates a text
shape on a double-click that lands on the canvas or on the locked screenshot. Without it the zoom
and a new text shape would both happen; the text tool is how text is drawn here.

### Driven

The 1500 x 500 grid fixture, frame `[60, 215, 1392, 465]`, select tool, `[web] ready protocol=10`.
A double-click at the global point `(1000, 600)` — 0.675 across the frame and 0.828 down it — left
`annotator.zoomLevel 2` and `annotator.zoomAnchor [0.675, 0.828]`, the click's own fractions, and
`page.shapes` stayed 1, so nothing was drawn. A second double-click at the same point left
`zoomLevel 1`: the frame it opened in.

Not driven: the refusals. The annotator was closed by a click in another app in the middle of that
round, twice, and the Mac was needed back before it could be rerun.
