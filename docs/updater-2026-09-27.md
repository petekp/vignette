# An updater, and testing it (2026-09-27)

Vignette cannot update itself. "Check for Updates…" opens the latest release on GitHub
(`Identity.releasesURL`), and nothing tells anyone a new version exists. Installs of 0.1.0 and
0.1.1 will never hear of a later version, so the first public build has to carry the updater.

## Recommendation

Add Sparkle 2 (2.10.0, released 2026-09-13). Most Mac apps outside the App Store use it. It reads
a feed of versions (an appcast), checks each download's EdDSA signature against a public key in
the app, and replaces the app in place. Vignette is not sandboxed, so Sparkle needs none of its XPC
services.

What the person sees:

- Vignette checks once a day, with no first-launch prompt asking permission.
- A new version shows as a gentle reminder, not a window that takes focus from the app you are in:
  a dot on the menu bar icon and a "Update Available…" item in its menu. That is Sparkle's
  `supportsGentleScheduledUpdateReminders`, meant for menu bar apps. Choosing the item opens
  Sparkle's own update window, with the release notes and Install.
- "Check for Updates…" checks at once and shows the same window.

## The changes that need approval

Release tooling needs approval for each change, so these are listed one by one.

1. **`project.yml`**: add the Sparkle package and link it to the app target, and add three
   Info.plist keys: `SUFeedURL`, `SUPublicEDKey`, and `SUEnableAutomaticChecks: true`. The
   `ReleasesURL` key goes, since nothing reads it once the menu item checks for updates.
2. **`scripts/release.sh`**: after notarizing and stapling the disk image, run Sparkle's
   `generate_appcast` over it. That signs the image with the EdDSA key from the Keychain and writes
   `build/dist/appcast.xml`. The printed next steps then upload both files to the release:
   `gh release create v$version "$dmg" build/dist/appcast.xml`.
3. **A signing key**, made once with Sparkle's `generate_keys`. The private key stays in your
   login Keychain and never enters the repo. The public key goes in `project.yml`. It needs a
   backup (`generate_keys -x <file>`, into your password manager): without it, no later version can
   reach an install that trusts this key.

The feed would be `https://github.com/petekp/vignette/releases/latest/download/appcast.xml`.
GitHub redirects that URL to the newest release's asset, so each release uploads one small file
and nothing else needs hosting. The site is not on GitHub Pages, so this is the simplest place
available.

Code changes, which need no special approval: an `Updater.swift` owning
`SPUStandardUpdaterController`, the menu item wired to it, the gentle reminder on the status
item, and the docs (AGENTS.md, `docs/building.md`).

## How it gets tested

On test copies only, never your install. Two builds of a test copy with its own bundle id
(`com.petepetrash.vignette.updatetest`), signed with your Developer ID, with a feed served from a
scratch folder on `127.0.0.1` and a test key kept apart from the release key. The first build is
installed, the second is published to the local feed, and each case below is driven and checked
with `[state]` and the log.

| Case | What is checked |
|---|---|
| The update | Found by a scheduled check and by the menu item; installs; the new version relaunches; `app.version` says so |
| Timing | An update chosen while the stack is open, while the editor is open with marks, and while a send waits for its answer |
| Declined | Skip This Version, Remind Me Later, a download that fails, no network |
| A bad download | An image whose signature does not match is refused |
| Settings | A file written by the old build loads; a `ui` default changed in the new build reaches it |
| Permissions | Accessibility stays granted; the folder permission holds; the login item opens the new version |
| Stored data | Drawings, open requests and replies waiting to be imported survive the relaunch |
| The skill | An older installed copy is rewritten by the first launch of the new version |
| Apple's screenshot settings | `appleOriginal` is kept and Restore still works |
| Where the app lives | /Applications, ~/Applications, a folder you cannot write to (Sparkle asks for a password) |

The last full check is a real release: 0.1.2 cut with the updater, then 0.1.3 reaching it through
the GitHub feed. 0.1.0 and 0.1.1 cannot be updated this way. Anyone on them downloads once more.

## Decided (Pete, 2026-09-27)

- All three changes above are approved.
- An update waits for Install: nothing installs by itself.
- The agent makes the key with `generate_keys` in Pete's login Keychain and exports a backup file
  for Pete to move into his password manager.

## Results (2026-09-27)

Built as planned and tested on a test copy: bundle id `com.petepetrash.vignette.updatetest`, signed
with the Developer ID, fed from `127.0.0.1` with a test key. Version 0.9.0 was installed in a scratch
folder and 0.9.1 was on the feed. Sparkle relaunches the new version with no environment, so both
builds set `VIGNETTE_SETTINGS` and `CFFIXED_USER_HOME` to scratch paths under `LSEnvironment`.

| Case | Result |
|---|---|
| The update found | By the check at launch. The dot came up, the menu showed "Update Available…" with 0.9.1, and `[state] app.update.waiting` said 0.9.1 |
| The install | Install Update, then Install and Relaunch. 0.9.1 was running 0.5 s after 0.9.0 quit, on the same scratch settings |
| Stack and editor open | A mark drawn just before Install and Relaunch was stored at quit (`[drawing] parked`), and 0.9.1 opened the drawing with both marks |
| Remind Me Later | The reminder cleared, and a relaunch showed none |
| Skip This Version | The next scheduled check reported nothing. Check for Updates… still offered 0.9.1 |
| A failed download | Sparkle's alert, "An error occurred while downloading the update". The app stayed on 0.9.0 |
| No network | A scheduled check logged one `[update] error` line and showed nothing. Check for Updates… showed Sparkle's alert |
| A wrong signature | "The update is improperly signed and could not be validated". The app stayed on 0.9.0 |
| Menu bar icon hidden | Sparkle showed its window itself, without activating the app |
| Settings | `ui.thumbnailSeconds`, set under 0.9.0, was kept. 0.9.1 changed the `toastSeconds` default, and the file did not gain that key |
| Stored data | The drawing from an agent's push survived |
| The skill | An older copy, version 4, was rewritten to version 5 by 0.9.1's first launch |
| Login item | Still `enabled` after the update |
| Apple's screenshot settings | `appleOriginal` unchanged |
| The dot | Fades out over about 0.25 s when the update window opens |

## Results on the real app (2026-09-30)

The notarized 0.1.2 image (build 474) was installed in a fresh macOS 15.7 VM as a Safari download,
moved to /Applications, and given Desktop access and Accessibility in setup. Its feed was pointed at
a local copy (`defaults write com.petepetrash.vignette SUFeedURL <url>`, which Sparkle reads ahead of
Info.plist) serving 0.1.3, build 475, signed with the release key.

| Case | Result |
|---|---|
| The update found | Check for Updates… offered 0.1.3 |
| The install | Install Update, then Install and Relaunch. 0.1.3 was running from /Applications 0.4 s after 0.1.2 quit |
| Accessibility | Still granted. The double tap opened the stack with no prompt |
| The folder permission | Still granted. A new capture on the Desktop was reported and copied |
| Setup | Not shown again |
| Login item | Still `enabled` |

After 0.1.2 was published, a fresh VM downloaded it from GitHub in Safari. The file matched the
release byte for byte, and the installed app's first check read the live feed: `[update] none:
You're up to date!`.

A second round on a fresh VM covered the last two cases in one update, from the same 0.1.2 to a
stand-in 0.1.3 (build 475):

| Case | Result |
|---|---|
| An app the person cannot write to | The app was made `root:wheel`. Install Update asked for an administrator's password, then installed. The new app kept `root:wheel` |
| A send waiting for its answer | A drawing was sent to a stand-in Claude Code session (an inbox with a live process, as `scripts/e2e` makes one) and left unanswered. 0.1.3 loaded the open request at launch, and the reply helper, now running 0.1.3's binary, was accepted and published the reply as a card |

A copy running from the disk image needs no case: opened from the image, Vignette moves itself to
Applications or quits (`AppLocation.swift`), so no copy runs from there.

Found on the way:

- The release key has its own Keychain account, `vignette`. The Keychain already held a Sparkle key,
  account `ed25519`, made 2026-01-19 for another app. A separate key means losing or leaking one
  does not affect the other.
- The Keychain asked for the login password when `sign_update` read the `vignette` key.
  `generate_appcast` read the test key without asking. So the first real release may ask once per
  Sparkle tool.
- One build into reused derived data stamped `CFBundleVersion` as 0, and Sparkle would offer any
  release to such a build. `scripts/release.sh` always builds into empty derived data.
